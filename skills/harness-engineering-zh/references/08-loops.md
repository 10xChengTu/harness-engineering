# 08 - Loops: 自主运行

把 Harness 变成一个自己运转的系统的模式——循环负责给 Agent 写 Prompt、检查它的工作成果，并判断何时该停下来。

## 第四次让渡

Prompt Engineering = 你怎么说。Context Engineering = 你给它看什么。Harness Engineering = 环境本身。**Loop Engineering = 系统如何自己转起来。**

每一层都包住前一层，而不是取代它。循环里依然有 Prompt——只是 Prompt 不再是你现场敲出来的话，而变成了循环每一轮自动组装出来的模板。

人的位置变了。**Sit on the loop, not in it（坐在循环之上，而不是循环之中）。** 剩下的工作只有两件：设计循环的各个环节和它的 STOP 条件，以及在循环停下之后审查交出来的成果。发现工作、写 Prompt、评判输出、决定要不要再来一轮——这些原本是人一轮一轮手动敲出来的，现在由循环自己组装。

## 循环的解剖结构

最简版本：gather context → take action → verify work → repeat（收集 Context → 采取行动 → 验证工作 → 重复）。

完整版本有六个环节：

```
DISCOVER  → 发现工作（失败的 CI、新 issue、TODO 清单）
ASSEMBLE  → 组装这一轮的 Prompt + Context
ACT       → 执行
VERIFY    → 跑验证器
PERSIST   → Commit、更新状态文件
DECIDE    → 继续循环，或 STOP
```

DISCOVER 和 ASSEMBLE 曾经是人手动敲 Prompt 的环节。VERIFY 和 DECIDE 曾经是人读输出、决定下一句话怎么说的环节。剩下的部分——Agent 干活本身——没有变。

## Routine vs Workflow vs Loop

不是所有无人值守运行的东西都叫循环。

| | Routine 例程 | Workflow 工作流 | Loop 循环 |
|---|---|---|---|
| 步骤 | 固定不变 | 按发现分支 | 动态迭代 |
| 停止条件 | 步骤走完 | 路径走完 | 验证器判定目标达成 |
| 自我检查 | 无 | 弱或无 | 核心机制 |
| 例子 | 定时跑 lint 并发报告 | CI 失败 → 分类 → 派单 | 修到 `test/auth` 全绿为止 |

唯一有意义的判据：**它会不会检查自己的工作，并据此决定是否继续？** 一个每晚跑 lint、发报告的定时任务是 Routine——它从不问"这修好了什么问题"。一个反复跑 lint、把 diff 和目标做对照、直到目标达成才停下来的循环是完全不同的一类系统——哪怕驱动它的代码看上去很像。

## Verifier 是承重墙

**循环的价值上限由 Verifier 决定，不由模型决定。** 没有可靠的"完成了吗"判据，一个循环要么永远停不下来，要么在错误的地方停下来，还自信满满地宣布成功。

搭建顺序：Verifier 先于循环。先把机器可以跑的东西立起来——测试套件、类型检查、diff 范围检查——再往上套循环。用更强的模型去配一个弱 Verifier，只会让自信的错误答案产生得更快。

| | 坏的停止条件 | 好的停止条件 |
|---|---|---|
| 例子 | "改进这段代码" | "`test/auth` 下所有测试通过，且 lint 干净" |
| 可检查性 | 只能靠感觉 | 机器一跑便知 |
| 循环行为 | 永远不知道何时停 | 有明确的出口 |

**Checker 绝不能是 Maker 本人。** 这条铁律也适用于停止条件本身——由一个独立的 Evaluator（通常是更小、更快的模型）判定"完成了"，而不是让写代码的那个模型自己宣布。参见 `04-multi-agent.md`（Generator-Evaluator）。

写代码的模型不适合给自己的代码打分——自我评估的偏差只往一个方向走，就是偏宽松。一次独立的第二遍审查，才能抓住第一个 Agent 已经说服自己接受的问题。

## 四种失败模式

无人值守运行的循环，失败的方式和被人逐轮盯着的 Agent 不一样——失败有空间可以在被发现之前一直跑下去。

| 失败模式 | 典型案例 | 对策 |
|---|---|---|
| Reward hacking（钻空子） | 删掉失败的测试，让 CI 变绿 | Verifier 同时检查"测试数量没有减少"；明确写下规则：删除或修改测试来让它通过是不可接受的 |
| 幻觉式成功 | Agent 自报"已完成"，实际没跑通 | "完成"是一个声称，不是证明——只信确定性 Verifier，永远不信自我汇报 |
| 误差随轨迹复利 | 第 3 轮的小错误，到第 15 轮变成大坑 | 每轮小步 Commit + 每轮独立验证，让错误早暴露 |
| 成本爆炸 | 循环空转一整夜，账单四位数 | 三条护栏（见下节） |

这四种都不是什么冷门情况。任何一个上线第一周的循环都可能撞上全部四种，而且都是提前设计比事后凌晨三点排查便宜得多。

## 三条护栏（上线第一天就要装）

没有护栏的循环不是资产，是负债。

1. **Iteration cap（迭代次数上限）**——对轮数设一个硬上限，这样一个卡住的循环不会仅凭一个 bug 就无限跑下去。
2. **Progress detection（进展检测）**——连续 N 轮没有可度量的进展（diff 为空、通过的测试数不变）就停。第 10 轮没动起来的循环，不会因为跑到第 40 轮就突然动起来。
3. **Budget cap（预算上限）**——对花费（token 或金额）设一个硬上限，一到就停，不为"眼看就要做完了"网开一面。

这三条装起来都很便宜，省掉的代价却很高昂。它们都不需要模型变得更聪明——只是把一次蠢失败能造成的损失，控制在被人发现之前的范围内。

## Fresh-Context 迭代（Ralph 模式）

这项技术得名于作者对《辛普森一家》某个角色的偏爱。最简实现：

```bash
while :; do cat PROMPT.md | agent ; done
```

就这么多——一个死循环，把同一个 Prompt 文件反复喂给 coding agent。核心设计选择：每一轮迭代都是全新的 Context。Progress lives in the repo, not in the model's memory（进展"长"在仓库里，而不是靠模型"记住"）——状态被外置到 git 和计划文件，模型永远不需要"记得"任何东西。每一轮迭代醒来，读 spec、看仓库当前状态、做一件事、Commit、然后结束；下一轮迭代会从 git 里接手前一轮留下的一切。

操作纪律：
- **每轮只做一件事**——避免单轮迭代把 Context 窗口撑爆。
- 每一轮都以确定性的方式重新装配同一套 Context 栈（specs + `fix_plan.md`）。
- 把主 Context 当调度器用——把高 Context 消耗的活（搜索、跑测试）派给 subagent。
- 维护 `fix_plan.md` 作为循环的外部任务清单；把 Agent 学到的项目知识写回 `AGENTS.md`。
- 要求"改动前先搜代码库"——永远不要假设某个功能没实现；正是这种假设导致了重复实现。
- 每次改动都留下一句"why this matters"的注释——下一轮迭代看不到这一轮的推理过程，只能靠这轮留下的纸条。
- 兜底手段：频繁 Commit、打 tag；一旦某次运行跑偏了，`git reset --hard` 后重跑——比人工调试划算。

**适用边界：Greenfield（从零开始的）项目，大致从 0 做到 90% 左右。不要对存量生产代码库使用这套方法。** Context Reset 的谱系参见 `06-long-running.md`。

## Loop Stack（循环栈）

单个 Agent 循环从不孤立运行——它通常嵌套在另外三层时间尺度依次变慢的循环里，每一层都在监督它下面的那一层。

| 层级 | 时间尺度 | 是什么 | 例子 |
|---|---|---|---|
| L1 Agent 循环 | 秒–分钟 | 模型 + 工具，最基础的循环 | 执行单次任务 |
| L2 验证循环 | 分钟 | Grader 按 rubric 打分，带反馈重试 | 测试 / 类型检查 / LLM-as-judge |
| L3 事件驱动循环 | 小时–天 | Agent 挂在真实事件源上，持续运行 | Cron、webhook、CI 失败、聊天消息 |
| L4 自我改进循环 | 周 | 分析 Agent 读生产 trace，回头改写内层配置 | trace 分析 → 更新 prompt/tools/rules |

两个值得点出的关键点：
- L2 的 Grader 应该先用确定性检查（便宜：链接可达、CI 通过、diff 未越界），再考虑上 LLM-as-judge。
- L4 的反馈不是绕回起点重新开始，而是**直接改写 L1 的 prompt/tool/config**。复利效应发生在 L3/L4——多数团队过度投资在 L1/L2 上。

人类监督不是"要不要"的二选一问题，而是"嵌在哪一层"的问题：L1 里高危操作前需要确认；L2 里由人补充 Grader；L3 里输出发布给终端用户前需要审批；L4 里配置变更上线前需要评审。

## 什么时候该上循环

两条轴决定要不要上循环：能否用机器验证"完成"，出错的代价有多大。从"可重复、机器可验证、炸半径小"的任务起步：依赖升级、lint 债清理、flaky test 排查、测试覆盖补齐、PR babysitting。

毕业标准（扩大权限范围前必须达标）：无人值守跑满一周、预算零超支，且产出的 PR 经人工 review 后 90% 以上可直接合并。

不要从相反的象限起步——一次性、难以机器验证、出错代价高的工作。这正是那种会跑很久、产出一个自信却错误的结果、并在被人发现之前就被合并进去的循环的典型画像。

并行度约束：真正的瓶颈是人的 review 带宽，不是算力。Worktree 解决的是 Agent 互相踩文件的问题——解决不了"谁来看"这件事。如果依然只有一个人要读完它们产出的每一个 PR，同时跑十个循环也没用——那只是把队列从"Agent 时间"挪到了"review 时间"。

## Comprehension Debt（理解债务）

循环跑得越快，"存在的代码"和"你理解的代码"之间的鸿沟就拉得越大。

由此衍生出两个风险：验证的责任不会因为循环说"完成了"就自动消失；以及 **cognitive surrender（认知投降）**——循环转得越顺畅，人越容易放弃自己的判断，直接对它交出来的东西照单全收。

对策：在流程里嵌入强制性的理解检查点——让 review 留在循环里、对产出做抽样精读而不是扫一眼 diff 就过、要求 Agent 对非平凡的改动附上解释。

两个人可以搭出一模一样的循环，却走向截然相反的结果：一个人用它在自己深刻理解的工作上跑得更快，另一个人用它彻底逃避理解这份工作。循环本身分不清这两者的区别，只有操作它的人才知道。

去搭建循环。但要以"打算继续留任工程师"的人的方式去搭它，而不是只做那个按下启动键的人。

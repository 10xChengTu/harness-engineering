# 07 - Diagnosis: 当 Agent 表现不佳时

当用户对 Agent 的输出感到沮丧时，问题几乎总是出在 Harness 上，而不是模型本身。本指南旨在帮助识别并修复根本原因。

## 症状 → 根本原因映射表

| 用户抱怨 | 可能的 Harness 缺失 | 修复方法 |
|---|---|---|
| "它一直犯同样的错误" | 没有阻止该错误的 Constraint | 添加 Lint 规则 / 类型检查 / 测试 |
| "它不遵守我们的约定" | 约定未记录或不可发现 | 在 docs/ 中编写约定，并在 AGENTS.md 中引用 |
| "它破坏了原本正常的功能" | 缺乏回归测试 | 在修改前为现有行为添加测试 |
| "它偏离了主题" | 任务范围或功能列表不明确 | 添加结构化功能列表 / 执行计划 |
| "它写的代码很平庸" | Context 中缺乏优秀代码示例 | 在 DESIGN_NOTES.md 中添加代码示例 / 模式 |
| "它忘记了我们讨论过的内容" | 跨会话 Context 未持久化 | 将决策写入文件，使用 progress.md |
| "它过早宣告完成" | 缺乏验证步骤 | 添加清单、测试、Evaluator Agent |
| "它使用了错误的模式" | 代码库中存在竞争模式且缺乏引导 | 记录在何时使用何种模式 |
| "输出质量不稳定" | 缺乏评估/反馈循环 | 添加 Eval 系统、GC Agent |
| "它耗时太长且成本太高" | Harness 过度工程化或架构错误 | 简化 —— 移除不产生价值的 Harness 组件 |

## 诊断流程

### 第一步：识别层级

询问：Harness 栈的哪个环节出现了故障？

1. **Context**：Agent 没有获得正确的信息
2. **Constraints**：没有阻止 Agent 出错的约束
3. **Feedback**：Agent 不知道自己失败了
4. **Architecture**：单 Agent 无法处理任务的复杂性
5. **Scope**：任务太大或过于模糊

### 第二步：最小化修复

应用针对根本原因的最小改动：

- 缺失 Context → 添加一个文档文件或 DESIGN_NOTES.md
- 缺失 Constraint → 添加一条 Lint 规则或测试
- 缺失 Feedback → 添加一个验证步骤
- 架构问题 → 拆分为两个 Agent（仅当单 Agent 确实无法处理时）
- 范围问题 → 将任务分解为更小的部分

**不要过度设计修复方案。** 针对每个错误建立一条规则。不断迭代。

### 第三步：验证

应用修复后：
1. 重现原始问题场景
2. 确认修复方案能阻止该问题发生
3. 确认修复方案没有破坏其他功能

## 常见的 Harness 改进（按影响力排序）

### 高影响，低投入
1. **添加 AGENTS.md**（如果缺失） —— 立即提升 Agent 的定位感
2. **针对重复性错误添加一条 Lint 规则** —— 预防整类错误的发生
3. **为损坏的行为添加测试** —— 立即捕获回归
4. **记录 Agent 一直违反的约定** —— 消除猜测

### 高影响，中投入
5. **创建带有架构概览的 docs/** —— 减少架构错误
6. **添加 pre-commit hooks** —— 在问题复合之前捕获它们
7. **设置进度跟踪** —— 防止过早完成和范围漂移
8. **在关键目录中添加 DESIGN_NOTES.md** —— 提供即时 Context

### 高影响，高投入
9. **实现 Evaluator Agent** —— 用于质量关键或主观任务
10. **构建自定义 Linters** —— 用于项目特定的架构约束
11. **创建 Eval 套件** —— 系统化的质量衡量和回归检测
12. **设置 GC Agent** —— 定期的一致性检查

## "每个错误建立一条规则"的纪律

每当 Agent 犯错时：

1. 修复眼前的问题
2. 询问："是否有一条规则可以永久防止这种情况？"
3. 如果是 → 添加规则（Lint、测试、类型或记录在案的约定）
4. 如果否 → 添加 Context（文档、示例、DESIGN_NOTES.md）

随着时间的推移，Harness 会积累起能够防止 Agent 犯过的每一个错误的规则。对于已知的失败模式，错误率将趋于零。

## 何时简化

Harness 过度工程化的迹象：
- Agent 花在遵守 Harness 规范上的时间超过了实际工作时间
- 对同一事物存在多个冗余检查
- Harness 规则从未触发（模型已经通过学习跨过了这些坎）
- 成本/时间显著增加，但质量提升不成比例

**当模型不再需要时，请移除 Harness 组件。** 模型在进步 —— 昨天的脚手架就是今天的累赘。

## Harness 作为数据集

Agent 的每一次交互都是一个训练信号。Harness 捕捉到了这些痕迹：
- Agent 尝试了什么
- 什么行得通
- 什么失败了
- 修复方案是什么

这些痕迹是你的竞争优势。它们是让你的 Harness 随时间变得更强大的数据。
